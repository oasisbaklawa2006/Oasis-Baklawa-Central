# Appverse autonomous release governance — implementation

This work adds a **trusted, exact-head merge eligibility check**. It does not merge PRs or deploy migrations. Main programme ledger: Central issue #437. A merged PR is never equivalent to Appverse launch certification.

## Merge actuator vs. gate evaluation — three different things

1. **Gate evaluation (this PR).** `Appverse Merge Gate` is a read-mostly *evaluator*: it publishes one check-run on the exact PR head. It never merges, never enables auto-merge and never changes a ruleset. This is enforced structurally: `api()` refuses every write except `POST /check-runs` and read-only GraphQL, and unit tests assert there is no merge/auto-merge endpoint in the source.
2. **Native auto-merge activation (not in this PR).** Enabling GitHub auto-merge on a PR is a separate, later action. It stays **disabled** and must not be enabled on #655 or any other PR until the activation conditions below are certified.
3. **The existing hourly ChatGPT/Release controller.** It is an independent actuator with its own authority; a passing gate does not grant it new powers, and this PR does not change it.

### Governance chain and activation conditions

Owner → GPT Governance (issue **#657**) → Claude/Cursor execution → GitHub independent verification → Protected merge.

This PR is **not** permission to bypass the planned GPT Governance Gate under #657. Unattended merging must not be activated until **all** of: independent human/code-owner review of this PR; trusted check enforcement certified (Phase 2 below, including a dedicated-identity decision for the gate check); the GPT Governance Gate under #657 implemented and certified; and the GitHub rulesets verified. Until then the controller keeps its fail-closed behaviour and a green gate check is *eligibility evidence only*.

## Two-phase activation — mandatory

**Phase 1 — Review and merge this infrastructure PR.** `.github/workflows/appverse-merge-gate-ci.yml` runs offline tests on the candidate branch. The new `Appverse Trusted Merge Controller` workflow does not run on `main` until this PR itself is approved and merged under existing protections. Do not add the new required check to GitHub rulesets until the workflow is live on `main`. Enabling it earlier can deadlock the infrastructure PR.

**What merging Phase 1 does and does not change.** It adds no merge authority, enables no auto-merge and changes no ruleset, App permission or environment. It is not entirely inert: once on `main` the controller workflow runs on its `schedule` (every ten minutes) and on completion of the watched workflows, and publishes the *advisory* check `Appverse Merge Gate (advisory)` with `checks: write`. The authoritative job runs only if the repository variable `APPVERSE_GATE_PUBLISHER` is set to `actions-environment`. An administrator must confirm **before the merge** that this variable is unset or set to an explicit disabled value that differs from `actions-environment` **case-insensitively**, because GitHub Actions string equality ignores letter case (`Actions-Environment` also enables the job) and the workflow can run as soon as it reaches `main` (this session could not read it; a read by the reviewer returned HTTP 403). If it cannot be read, record that and treat the merge as not yet cleared on this point.

**Phase 2 — GitHub administrator must enforce Central rule #19200597.** Open GitHub Settings → Rules → Rulesets → **Require CI checks on main** (ID `19200597`), add `Require status checks to pass`, require exact `Appverse Merge Gate` **from the dedicated GitHub App (integration ID 5645415), never from the shared GitHub Actions app (15368)**, and select `Require branches to be up to date before merging` (strict). Retain existing Central main release governance rule #19820724, including required review, dismiss-stale and thread-resolution rules. **Also enable `Require review from Code Owners` on #19820724**: `.github/CODEOWNERS` covers the merge controller, every `.github/` file, the CI evidence producers and the Finance/auth/dispatch/stock authority areas, so ordinary application PRs outside those areas can still use autonomous independent review while sensitive areas always need a human code owner (tests fail if a sensitive tracked file lacks a CODEOWNERS rule). Verify there are no bypass actors. GitHub App connector has no admin write action, so these settings changes are not performed by this PR. Remove any applicable merge-bypass actors from the CI ruleset; an unchecked bypass defeats unattended protection.

**Fail-closed handshake:** the gate returns FAIL until ruleset #19200597 strictly requires its own check. It cannot declare merge eligibility based solely on voluntary/informational green CI.

## What is automated

- Event sources: completion of relevant CI workflows, ten-minute reconciliation and manual dispatch. These events execute the trusted workflow from default main; PR-review changes are picked up by the scheduled reconciliation. No privileged `pull_request_target` code is executed.
- The controller executes **trusted main**, with no checkout or execution of candidate branch code under write credentials. It has only `checks:write`, not `contents:write`, `issues:write` or `pull-requests:write`.
- It publishes a uniquely named `Appverse Merge Gate` check-run on the PR's exact current head, rejecting missing, skipped, stale or failing checks. For each checked GitHub App it checks the actual app slug, not merely the display name; it also validates the verified Snyk and Vercel status creators. It checks CodeRabbit (zero actionable current-head comments), Cursor Security and Approval, Codacy, relevant CodeQL languages, scope-relevant Factory/Buyer/Point100 suites, release quality, secret/ownership, current-head independent approval and all resolved review threads.
- The **required Appverse Merge Gate check is published for every open PR targeting `main`**, including unlabelled PRs; relevant runtime suites are chosen from changed paths (factory changes also require Point100). The separate `appverse-gated` label only opts an eligible PR into **native automatic merge**. Neither a label nor a bot review bypasses required checks.
- It refuses drafts, stacked PRs, evidence-only #651, Core-owned SQL migrations in Central and changed SHA/base during validation.
- **Sensitive-path rule.** A conservative classifier (`sensitive_paths`) marks Finance/payment/settlement, authentication/RBAC/RLS/roles/sessions, Dispatch and Gate authority, stock authority, `supabase/`, every `.github/` file (all workflows and CODEOWNERS), the CI evidence producers (`scripts/*-certification/`, `tests/point100|factory-certification|buyer-certification/`, `.appverse/`), deployment/config/dependency manifests (`vercel.json`, `package.json`, lockfiles) and governance documents as sensitive. Renames are classified by both the old and the new path. If any changed path is sensitive, the gate requires a distinct, independent, trusted **human** code-owner `APPROVED` review on the current head (login in the CODEOWNERS owner set *and* `OWNER/MEMBER/COLLABORATOR` association, not the PR author). A bot or AI approval, including Cursor, never satisfies this; bot or AI approval never substitutes for the human code owner. Ordinary application PRs may still use the trusted Cursor approver. The rule is over-inclusive by design: a false positive costs a human review, a false negative would let a bot approve a Finance/auth/Gate change.
- **Scope-aware CI.** Lane requirements (Buyer / Factory / Point100) are derived from the *same path filters the lane workflows use*; `tests/appverse-control/test_workflow_policy.py` fails if they drift. A required check that is missing, skipped, neutral, cancelled, timed-out, pending or posted by a different app counts as **not passing**. In addition, *any other* check on the head that is failing or still running (except this gate itself and jobs explicitly named `(advisory)`) blocks, so a lane the gate did not list can never fail silently.
- **Review evidence.** A green standalone `CodeRabbit` check is never evidence of a clean review. The gate reads CodeRabbit's review of the exact head: it must be a recognisable CodeRabbit review (not empty), must not request changes, must not report actionable findings (CodeRabbit prints `Actionable comments posted: N` only when N > 0; when the marker is absent the inline comments of that very review are counted and must be zero), and must list no `Failed pre-merge checks` (observed on #655 and #656: `Docstring Coverage`). Nitpicks alone do not block. A failed pre-merge check can be accepted only by adding its exact name to `ACCEPTED_PREMERGE_FAILURES` in the gate source, a code-owner-protected change that needs independent human approval; it is empty by default, so as certified a `Docstring Coverage` failure keeps the gate red.
- **Provenance.** Check-runs are matched on `(name, app slug)`; commit statuses on `(context, creator login)` with the newest status chosen by `updated_at`/`id`, not list order. The authoritative `Appverse Merge Gate` must be pinned to the dedicated App's `integration_id` 5645415 (a pin to the shared Actions identity 15368, an unpinned entry, or a mixed list is reported as unsafe), and a same-named check from any other app is reported as `SPOOF_ATTEMPT`. A missing `bypass_actors` field (token cannot see it) is treated as *unverifiable*, never as "no bypass".
- Failed evidence is shown in the PR check summary. The controller itself **never merges**, cannot turn GitHub protection off, and cannot deploy production.
- Native GitHub auto-merge can be enabled **per PR only after phase 2**. GitHub itself enforces check and approval; the existing hourly autonomous controller may select fully authorized PRs for auto-merge.

## Residual risk and hardening decisions for the owner

- **Publisher identity (resolved by design, activation pending).** The shared GitHub Actions identity can be impersonated by any workflow that can request `checks: write`, so it no longer has any authority: the Actions job publishes only `Appverse Merge Gate (advisory)`, which must never be required, and `APPVERSE_PUBLISH_MODE=advisory` refuses to run if the dedicated App credential is present. The authoritative `Appverse Merge Gate` is published only by the dedicated GitHub App (ID 5645415), either from the Cloudflare Worker `oasis-appverse-merge-gate` or from the opt-in `authoritative-publication` job (repository variable `APPVERSE_GATE_PUBLISHER=actions-environment`). That job reads the App key from the environment `appverse-merge-gate`, and the script **withholds publication unless that environment is verifiably restricted to deployments from `main`** (a branch workflow could otherwise read the key). Withholding publication publishes nothing, and publishing nothing does **not** block merging: an earlier authoritative SUCCESS on the same head stays in force (see "Freshness of an authoritative SUCCESS"), which is why native unattended auto-merge stays disabled until an enforceable freshness mechanism is certified. A Worker publisher must implement the same policy; until it demonstrably authenticates, the in-repo job is the only implemented authoritative path. The ruleset must then pin 5645415. **Single authority and name:** the only authoritative identity is GitHub App 5645415 publishing the exact check name `Appverse Merge Gate`. The Cloudflare Worker's source was reported to use `Oasis Appverse Merge Gate`; with that name the ruleset is never satisfied (merging stays blocked, which is safe but useless), so the Worker must be changed to publish `Appverse Merge Gate`. The gate makes the mismatch visible: any check published by App 5645415 under another name is reported as `NAME_MISMATCH`. Not complete until the owner performs the activation checklist below and the live negative spoof test passes.
- **Native code-owner coverage.** Prefix-scoped areas plus 53 literal-case vocabulary rules (GitHub CODEOWNERS has no character classes, so every word appears in its capitalised and lowercase form) now cover the authority code under `src/` and `scripts/` (Finance, payments, auth/roles/sessions/tokens, RBAC, dispatch and Gate authority; tests fail on drift or unsupported syntax). Of the 229 files previously covered only by the gate, 118 are now natively owned; about 120 files in total are under two-person review, almost all in authority areas. Still gate-only (human approval required, no native rule): about 40 archived WhatsApp reference tests, `src/vite-env.d.ts`, documents and ledgers, `android-tv/` and similar non-runtime files, plus a few over-matches such as `src/lib/provider-preview-uat/gates*`. Extending native ownership to those is an owner decision about review load. **Matching model:** GitHub's documented semantics are used in the tests (a trailing `/` or a literal directory name covers everything beneath; a wildcard final segment matches only that entry and does not descend, so every wildcard file rule has a trailing-slash directory twin). The tests model that documentation; they do not call GitHub's matcher. After merge, confirm with `GET /repos/{owner}/{repo}/codeowners/errors` (syntax) and by opening a throwaway PR that touches `src/FinanceFolder/x.ts` and `src/lib/finance-authority/x.ts` to see the requested owners.
- **Bypass-actor attestation.** `bypass_actors` is only returned to callers with administration read, which the workflow `GITHUB_TOKEN` does not have. The authoritative job therefore mints the dedicated App's installation token with `administration: read` (read-only) and `checks: write`, and ruleset reads use it. If the field is still hidden the gate reports `bypass_actors not visible to the controller token` and stays red; a missing field is never treated as "no bypass actors".
- **Test merge commits.** Required checks for `pull_request` workflows are attached to the PR *head* SHA (verified: Release Quality Gate appears on the head commit), so publishing the gate on the head SHA matches what the ruleset evaluates. Confirm once in the merge box before activation.
- **Latency.** The gate responds to completion of watched workflows and has a **scheduled ten-minute reconciliation interval, not a guaranteed maximum delay**: GitHub may delay or drop scheduled runs, and publisher failure may leave a new head without any gate check indefinitely. An absent check prevents merging **only once ruleset #19200597 requires the check and no bypass actor applies** (Phase 2); before that, in Phase 1, the gate is not required and its absence blocks nothing. Even then the delay protects only a head that has *no* authoritative check yet; it says nothing about a head that already has an authoritative SUCCESS (see the freshness section).
- **Observed state at certification time:** ruleset #19200597 has an admin bypass actor and no `required_status_checks` rule; ruleset #19820724 has `require_code_owner_review=false`. The gate therefore correctly reports `BLOCKED_RULESET`. These are administrator settings that no PR can or should change.

## Freshness of an authoritative SUCCESS: what can and cannot be enforced

**Stated plainly:** an absent or failed publisher cannot invalidate a prior authoritative SUCCESS on the same head, so *requiring the check alone cannot protect unattended merges*. Unattended merge commissioning remains **prohibited** until an independently enforced merge-time freshness protection is deployed and certified by an administrator. No timeout, re-poll, advisory check or renamed check in this repository substitutes for that.

A required status check is matched by name and publishing app on the PR head SHA. GitHub gives it no expiry, and only its publisher can supersede it. Consequences, each reproduced by an offline test (`StaleAuthoritativeSuccessTests`):

| Situation on a head that already has an authoritative SUCCESS | What the code does | Enforceable? |
|---|---|---|
| Approval revoked, review blocked, a check fails, threads unresolved, sensitive path needs a human | Publishes a FAILURE as the dedicated App, then reads back that it is now the newest authoritative check, else raises `SUPERSESSION_NOT_CONFIRMED` | Yes while the publisher runs (GitHub's "newest check wins" behaviour must be confirmed live) |
| Evidence cannot be read (rulesets, API errors, exceptions) | Publishes a FAILURE (`BLOCKED_GATE_VERIFICATION`) | Yes while the publisher runs |
| Publisher unavailable: App token missing, expired or rejected, environment not restricted to `main`, environment unreadable | Cannot publish anything. Fails the job loudly with `AUTHORITATIVE_PUBLICATION_WITHHELD` and states whether a prior SUCCESS exists and is now STALE | **No.** The earlier SUCCESS stays in force; nothing in this repository can revoke it |
| The idempotency lookup fails | Publishes anyway; an optimisation never suppresses a verdict | Yes |
| An identical earlier result exists | Skipped only while it is younger than half of `FRESHNESS_SECONDS` (1800); otherwise re-stamped | Yes |

**Therefore native auto-merge stays DISABLED**, and the design puts freshness in the merge actor, not in a required check. This is deliberately narrower than "fail-closed": pinning the SHA stops a later push being merged, but gate status, reviews, threads and other evidence can still change between evaluation and merge. The merge actor must therefore re-evaluate immediately before merging and enforce the result at merge time; nothing in this repository can enforce it for them:

1. immediately before merging, the actor runs `python3 scripts/appverse-control/appverse_merge_gate.py --evaluate PR --expect-sha HEAD_SHA` (read-only, publishes nothing; exit 0 eligible, 3 ineligible, 2 usage error). It requires `GITHUB_REPOSITORY=oasisbaklawa2006/Oasis-Baklawa-Central` and `GH_TOKEN` with read access to pull requests, checks, statuses, reviews, actions and repository rulesets (including ruleset bypass actors). Supply the token from a secret store or an interactive prompt into the process environment only; never put it on the command line, in shell history, in logs or in shared output;
2. it also requires the newest check named `Appverse Merge Gate` to pass `authoritative_success_problems` (dedicated App, exact head, completed success, not older than `FRESHNESS_SECONDS`);
3. it pins the merge to the evaluated SHA so a later push cannot be merged by accident.

Residual architectural blocker (not solvable by a PR): unattended native auto-merge would need a mechanism that makes an unrefreshed check invalid. Candidates, all administrator decisions: a merge queue (the check must then exist on the new merge-group SHA, which fails closed when the publisher is gone; merge queue availability for a user-owned repository must be verified before relying on it) or a ruleset "Require workflows to pass" rule. A webhook-driven publisher can shorten the stale window but cannot remove it. Do not enable auto-merge on any PR until one of those is in place and certified.

## Owner activation checklist (administrator actions; no PR can perform these)

1. **Dedicated App permissions** (App 5645415, installed on this repository): `checks: write`, `administration: read`, `pull requests: read`, `contents: read`, `statuses: read`, `actions: read`, `environments: read` (needed to verify the environment restriction). Nothing broader.
2. **Publisher path, choose one; either way the check name is exactly `Appverse Merge Gate`.** *Worker:* resolve the Worker's GitHub App authentication first (see the Worker diagnosis note in issue #660) and make it implement this policy. *In-repo job:* create the environment `appverse-merge-gate` with deployment branches restricted to **selected branches: `main` only**, add secret `APPVERSE_GATE_APP_PRIVATE_KEY` and variable `APPVERSE_GATE_APP_ID` to that environment/repository, then set the repository variable `APPVERSE_GATE_PUBLISHER=actions-environment`. Never paste the key anywhere else.
3. **Dispatch the controller once on `main`** and read both summaries: ruleset visibility (`bypass_actors`), environment verification, and that publication works as the dedicated App (app 5645415). Before step 5 the ruleset does not yet require the gate, so a BLOCKED authoritative result for that reason is the expected outcome; do not require an authoritative SUCCESS here. Verify a successful authoritative check only after step 5, once the ruleset requirement and code-owner review are in force.
4. **Live negative spoof test (must be run and recorded before any unattended merging):** the requirement must actually be in force for the test to mean anything, so run it either against a temporary ruleset that requires `Appverse Merge Gate` (integration 5645415) on a throwaway target branch, or after step 5 and before unattended merging is allowed. From a throwaway branch, run a workflow that posts a check named `Appverse Merge Gate` with `GITHUB_TOKEN`; confirm the gate reports `SPOOF_ATTEMPT` and that the ruleset does **not** treat it as satisfying the requirement, with no legitimate authoritative SUCCESS present on the head that could mask the result; delete the branch and any temporary ruleset.
5. **Rulesets.** #19200597: add `Require status checks` with `Appverse Merge Gate` pinned to integration 5645415, strict policy on, no bypass actors. #19820724: enable code-owner review, keep stale-review dismissal and thread resolution.
6. Only then consider #657 (GPT Governance) for any unattended merging.

**Blocking conditions:** gate not installed on main; missing mandatory ruleset; unapproved/changed head; tests pending/failing/skipped; unresolved reviews; mismatched Core authority; real physical/provider evidence absent. Such PRs must not auto-merge. No final live certification is claimed solely from CI.

## Two different certificates: offline code merge-ready vs live trusted auto-merge commissioned

| Certificate | Meaning | Status of this change |
|---|---|---|
| **OFFLINE #656 CODE MERGE-READY** | The inert software (controller, workflow definitions, tests, CODEOWNERS, this policy) has no known code defect, every offline negative test passes on the exact head, exact-head CI and reviewers are clean, and an independent human code-owner has approved that SHA. Merging it changes nothing about how any PR is merged. | May be claimed only for a specific final SHA, only after independent human approval. |
| **LIVE TRUSTED AUTO-MERGE COMMISSIONED** | A dedicated-App publisher is proven live, the rulesets enforce the gate with no bypass, and a freshness mechanism the merge actor cannot skip is certified. | **NO.** Not commissioned, not claimed, not implied by merging #656. |

Neither certificate is a substitute for the other, and `PR MERGED != STAGE CLEARED`.

### Review threads that stay HOLD after merge (precisely identified, impossible to verify before the code exists on `main`)

1. **Live `bypass_actors` attestation through the dedicated App installation token.** Code and offline tests already fail closed: a hidden field is *unverifiable*, never *empty*; any bypass actor, a pin to the shared Actions identity, an unpinned or mixed list, or a wrong integration id is reported; an unreadable ruleset publishes FAILURE. An owner/admin-capable token read is **not** equivalent to proof that the App token can read the field. Post-installation certification: authenticate App 5645415 from the `main`-only environment, dispatch the controller on `main`, and record that both rulesets' `bypass_actors` are visible to *that* token (otherwise the gate stays red and the requirement must not be enabled).
2. **Stale authoritative SUCCESS after a publisher outage.** A required check has no expiry; nothing in a PR can revoke an earlier SUCCESS when the publisher is down. Not solved by an early return, a re-poll, the 1800 s freshness text, an advisory check, a new check name, or a success check alone. Native unattended auto-merge stays **DISABLED** and no background merge actuator is added. Until a merge-time pinned-SHA revalidation is an enforceable deployed path (merge queue, a "Require workflows to pass" rule, or an equivalent certified by an administrator), the supervised merge actor must run `--evaluate PR --expect-sha SHA` and `authoritative_success_problems` itself.
