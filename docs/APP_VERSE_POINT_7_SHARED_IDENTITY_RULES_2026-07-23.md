# App-Verse Point 7 — Shared Identity Rules

**Date:** 2026-07-23  
**Status:** Frozen architecture rule  
**Scope:** Customer App, Central, AI Studio, Trace, Supabase Core and all external integrations

## 1. Core principle

Every real-world or business object has one canonical immutable internal identity. Human-readable references, legacy codes, barcodes, provider message IDs and external document numbers are aliases or references, not substitutes for the canonical ID.

## 2. Canonical ID standard

- Canonical entity IDs use UUIDs generated by the authoritative backend.
- IDs are immutable and never recycled.
- Frontends may request creation, but must not invent final authoritative IDs offline except as temporary client IDs.
- Temporary client IDs must be replaced through an explicit reconciliation mapping.
- Database primary keys must not encode mutable business meaning.

## 3. Identity layers

Each governed entity may carry four identity layers:

1. `id` — immutable canonical UUID.
2. `public_reference` or domain reference — human-readable stable business reference.
3. `legacy_reference` — historical system identifier retained for reconciliation.
4. `external_reference` — provider or partner identifier scoped by provider and account.

No external or legacy reference may be globally assumed unique without a namespace.

## 4. Namespace rules

All non-canonical identities must include a namespace or type, for example:

- `legacy:rancelab:customer:12345`
- `provider:meta_whatsapp:message:<id>`
- `provider:resend:email:<id>`
- `provider:msg91:request:<id>`
- `trace:barcode:CTN-SO-2026-0001`
- `business:order:SO-2026-0001`

The pair `(namespace, external_id)` must be unique.

## 5. Human-readable business references

Human-readable references are stable after issue and must not be silently changed.

Recommended patterns:

- Customer account: `CUS-YYYY-NNNNN`
- Quote: `Q-YYYY-NNNNN`
- Order: `SO-YYYY-NNNNN`
- Production batch: `BAT-YYYYMMDD-NNNN`
- Carton: `CTN-SO-<order-reference>-NNN`
- Dispatch: `DSP-YYYY-NNNNN`
- Support ticket: `SUP-YYYY-NNNNN`

Exact formatting may evolve only through a versioned contract. Existing references remain resolvable permanently.

## 6. Product identity

- Product, variant, pack and sellable SKU are separate entities.
- `product_id` identifies the conceptual product family.
- `variant_id` identifies a governed variation.
- `pack_id` identifies a packaging configuration.
- `sku_id` identifies the sellable/operational stock-keeping unit.
- SKU code is a stable business reference, not the primary key.
- AI Studio assigns and governs product identity; Central and Trace consume it.
- Retired SKUs remain resolvable and must not be reused for a different product.

## 7. Customer identity

A company, branch, contact, buyer login and delivery address are distinct identities.

- One company may have many branches.
- One branch may have many contacts.
- One contact may be linked to one or more authorised buyer accounts only through explicit membership.
- Phone number, email, GSTIN and WhatsApp identity are attributes or verified aliases, not primary identities.
- Customer merges require an auditable survivor record and alias mapping.

## 8. Order identity

- Every canonical order has one `order_id` and one stable order reference.
- Source drafts, WhatsApp packets, quotes and carts retain their own IDs.
- Conversion creates links; it does not overwrite the source identity.
- One source object may produce at most one live canonical order unless an explicit split conversion is recorded.
- Duplicate order prevention uses source identity, customer, line signature, time window and idempotency keys.

## 9. WhatsApp identity

The following identities are distinct and must all be preserved:

- provider message ID;
- sender WhatsApp account/phone;
- receiver business channel;
- original customer/company/contact;
- employee or intermediary sender;
- stitched conversation packet;
- governed intake/draft;
- resulting order or CRM item.

Fragmented messages share a packet/correlation identity but retain individual source message identities.

## 10. Trace identity

- Product label, batch label, pack label, carton label and shipment label are different identities.
- Barcode text is a representation of an identity, not the database identity itself.
- Reprinting preserves the same governed object identity while generating a new print-event ID.
- Replacement labels require supersession linkage and reason.
- A scan has its own immutable `scan_id` and references the scanned entity.
- Physical movement events never overwrite prior evidence.

## 11. Correlation IDs

A `correlation_id` groups all records belonging to one business transaction or workflow attempt across repositories.

Examples:

- WhatsApp intake → draft → order
- order → reservation → production → dispatch
- label request → print → scan → handover
- payment proof → review → finance release

Rules:

- generated at the first trusted boundary;
- propagated unchanged through downstream commands/events;
- never used as a primary key;
- searchable across all operational logs and audit records.

## 12. Causation IDs

Every emitted event should optionally record `causation_id`, pointing to the command/event that directly caused it.

This allows reconstruction of chains such as:

`order.approved` → `reservation.requested` → `reservation.created` → `production.queue.seeded`.

## 13. Idempotency keys

Idempotency keys protect write operations from replay and duplication.

- Keys are scoped to operation, caller/source and canonical target.
- A repeated request with the same key and equivalent payload returns the original result.
- Same key with a materially different payload fails closed.
- Keys must be signed or authenticated for cross-system calls.
- Retention must cover the maximum realistic retry window.

Examples:

- order submission;
- payment proof upload;
- WhatsApp packet conversion;
- barcode scan ingest;
- carton finalisation;
- label print request;
- dispatch finalisation.

## 14. Offline temporary identity

Handheld and mobile apps may create temporary IDs when offline.

Required fields:

- `client_generated_id`;
- device ID;
- operator ID;
- creation timestamp;
- entity type;
- idempotency key;
- payload hash.

On sync, the backend returns the canonical ID and stores the mapping. The client must not silently create a second object after a retry.

## 15. Device identity

Every operational device must have a stable registered `device_id` distinct from the user.

Device record includes:

- device type;
- platform/model;
- assigned location/department;
- trust status;
- app version;
- last seen;
- credential/key version;
- revoked/suspended state.

A user action records both actor identity and device identity.

## 16. Identity merge and split rules

### Merge

- choose one survivor canonical ID;
- retain all merged IDs as aliases;
- move relationships through a controlled migration;
- preserve original audit history;
- prohibit silent hard deletion.

### Split

- create new canonical entities;
- explicitly assign relationships to each new entity;
- retain the originating identity and split event;
- never mutate historical records to imply the split always existed.

## 17. Deletion and retirement

- Canonical IDs are not reused.
- Business entities are normally retired, suspended, archived or anonymised, not physically deleted.
- Hard deletion is permitted only where legally required or proven safe and must leave non-sensitive tombstone/reference protection where needed.
- External references belonging to deleted entities remain reserved unless a provider contract explicitly permits reuse.

## 18. Cross-repository contract

- Supabase Core defines ID formats, mappings and uniqueness constraints.
- Authoritative repositories create identities only for entities they own.
- Consumer repositories store canonical IDs and read projections, not shadow identities.
- Any local cache must preserve the canonical source ID and source version.
- Cross-repo payloads must include entity type, canonical ID, correlation ID and schema version.

## 19. Conflict resolution

When identities conflict:

1. preserve all source evidence;
2. stop automated mutation if ambiguity remains;
3. resolve through the authoritative domain owner;
4. create explicit alias/merge/supersession records;
5. never rewrite historical events to conceal the conflict.

## 20. Prohibited practices

- using phone/email/SKU/barcode as the database primary key;
- generating separate canonical IDs for the same entity in multiple repos;
- reusing retired order, SKU, batch or carton references;
- overwriting provider message IDs;
- deleting source records after conversion;
- treating correlation IDs as entity IDs;
- accepting replayed writes without idempotency enforcement;
- silently resolving duplicate customers or products.
